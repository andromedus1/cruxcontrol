# Catalog Bootstrap (consented offline install)

## Brief

Install a bounded, verified Fullride catalog snapshot after explicit consent, then
query it offline through the existing SQLite worker. Andrew accepted access to the
older legacy Kilter catalog first, with current-catalog access following. Label the
source and age honestly; neither this installation nor a new build date establishes
coverage of the current Kilter community.

This feature owns snapshot provenance, acquisition bounds, the OPFS import and
activation contract, recoverable status, and download-progress events. The existing
ignored snapshot is available for private local evaluation. No raw catalog enters
Git, public distribution, or automatic CI publication. The community-browser feature
owns consent UI, runtime wiring and update admission. Incremental sync, current
provider acquisition, and catalog browsing/filtering belong to their existing items.

## Design decisions — resumed 2026-10-09

- **Source:** Andrew accepted the legacy catalog first, then current Kilter access.
  Reuse the checked local artifact for this stride. Record its generation date
  (2026-06-14) separately from source-data freshness, which is unknown; never label
  the legacy dataset as current. Current source acquisition remains a separate gate.
- **Consent:** offer installation from the community entry surface with source,
  generation date, download/storage sizes, and offline-use explanation. No binary
  download, site-storage request, or installation occurs before confirmation.
  Metadata may be fetched to prepare that offer. Declining leaves local work usable.
- **No automatic replacement:** an installed valid catalog opens offline without a
  manifest fetch. A version/digest difference can be offered for explicit installation;
  it never silently replaces the active catalog. Incremental sync stays out of scope.
- **VFS:** retain pinned wa-sqlite 1.0.0, its synchronous WASM build, and
  `AccessHandlePoolVFS`. Public VFS methods import the bytes; no `importDb`, private
  pool header, prebuilt pool, new dependency, or VFS migration is needed.
- **Activation:** write and validate an inactive fixed slot, then atomically commit
  a small receipt naming it. Keep the prior active slot intact until a later consented
  install needs that inactive slot. A failed install never overwrites the active slot.
- **Concurrency:** one catalog worker owns the VFS per origin at a time. Acquire an
  exclusive Web Lock before constructing the pool and retain it through final close.
  Allow a bounded startup handoff before reporting busy; another tab's authored
  library remains usable while catalog ownership is unavailable.
- **Scope:** retain the query-only `CatalogPort`; add installation/status capability
  separately at the adapter/RPC edge. Reuse the current library, board, update-admission,
  and controller boundaries. No local-climb or playlist database/schema changes.

## VFS spike — passed 2026-10-09

Grounding: inspected the installed primary implementation
`node_modules/wa-sqlite/src/examples/AccessHandlePoolVFS.js`, its `README.md`,
`OriginPrivateFileSystemVFS.js`, `VFS.js`, the project `CatalogDb`, worker, RPC,
adapter, and tests. The published SQLite contracts define
[VFS open/access/delete](https://sqlite.org/c3ref/vfs.html) and
[file write/truncate/sync/close](https://sqlite.org/c3ref/io_methods.html).
The installed JavaScript implementation, rather than an assumed high-level import
helper, establishes the concrete argument shapes used below.

An isolated Chromium **151.0.7922.34** dedicated worker imported the existing ignored
gzip through `xOpen → xTruncate → chunked xWrite → xSync → xClose`, then opened the
logical filename READONLY with the existing synchronous WASM build. The spike used
a new temporary browser profile and a separate OPFS directory, with no authored data.

| Check | Observed result |
| --- | --- |
| Artifact integrity | SHA-256 matched the committed manifest; 5,122,102 compressed and 12,410,880 raw bytes |
| Initial imported database | 23,156 climbs; 43,740 climb_stats; `PRAGMA integrity_check` = `ok` |
| Close VFS, new worker and page reload | Same counts and integrity result; no download/import |
| Full browser exit and restart with temporary profile | Same counts and integrity result; no download/import |
| Inject partial candidate write, then close/delete candidate | Candidate absent; active counts unchanged and integrity `ok` |
| Import invalid SQLite candidate, then validate/close/delete | Rejected as `file is not a database`; active database unchanged |
| Negative control: omit `SQLITE_OPEN_MAIN_DB` at creation | File exists during the first worker, but VFS reset discards it on reopen |

**Required flags:** `SQLITE_OPEN_CREATE | SQLITE_OPEN_READWRITE | SQLITE_OPEN_MAIN_DB`.
`MAIN_DB` is essential because pool recovery only retains persistent file types.
Use a reserved manual file identifier (`-1`, never concurrently with another manual
import), check every SQLite result code, catch thrown I/O exceptions, and always
close the manual handle in `finally`. `xClose` flushes but does not release the pool's
OPFS handles; after all SQLite connections close, call `vfs.close()` as well.
Delete failed candidates only after their raw and SQLite handles close. Do not delete
the directory or inspect/modify its opaque file layout.

The source confirms `OriginPrivateFileSystemVFS` routes open/read/lock operations
through `handleAsync`; switching to it would also require the async WASM pairing.
The absence of `importDb` never established that the existing VFS could not import.

Temporary reproduction files and detailed results are at
`/tmp/crux-vfs-spike-20261009/{worker.js,run.mjs,results.json}` for this session.
They are not durable CI evidence. The production acceptance test below must reproduce
the public-method import/reopen checks with a committed synthetic SQL fixture.

A second synthetic browser spike exercised the two-slot protocol with one-row and
two-row databases. Killing the worker after candidate validation but before receipt
commit reopened the one-row active slot; killing it after the strict-durability IDB
transaction completed reopened the two-row candidate. While an owner held the Web
Lock, another worker returned busy before pool construction; after owner close,
the next worker acquired the lease and queried the committed two-row database.
Evidence: `activation-worker.js`, `activation-run.mjs`, and
`activation-results.json` in the same temporary directory. These are feasibility and
failure-boundary observations, not evidence of production implementation, UI, or bundling.

## Architectural choice

**Chosen: existing synchronous VFS, two immutable-at-runtime slots, and one active receipt.**
Candidate filenames are `catalog-a.sqlite3` and `catalog-b.sqlite3`, inside the existing
`cruxcontrol-catalog` pool. The receipt lives in a new catalog-only IndexedDB database,
`cruxcontrol-catalog-metadata`, with one `active` store and one `kilter-fullride-7x10`
key. It owns only slot identity and provenance; SQLite remains the community read model.
The two fixed names bound abandoned candidates without an orphan registry or private rename.

Alternatives considered:

1. **Switch to `OriginPrivateFileSystemVFS` plus async WASM:** possible, but changes the
   proven readpath and locking/runtime combination without a needed capability gain.
2. **Import into memory then copy tables/backup:** adds schema-copy behavior and extra
   memory while backup/deserialization exports would need separate verification. Direct
   VFS import already preserves the snapshot exactly.
3. **Existing VFS public methods (chosen):** the browser spike proves feasibility and
   persisted reopen. Separate slots supply replacement safety that a direct overwrite
   of `catalog.sqlite3` would lack. No compatibility migration is invented for the
   unused old single filename; pre-existing unrecognized files are not deleted.

### Unit 1: VFS import and activation — trickiest, implement first

**Files:** `web/src/data/sqlite/catalog-install.ts`,
`web/src/data/sqlite/catalog-receipt.ts`, `web/src/data/sqlite/catalog-config.ts`,
`web/src/data/sqlite/wa-sqlite-vfs.d.ts`, `web/src/data/catalog/schema.ts`.

```typescript

export interface CatalogReceipt {

  slot: CatalogSlot;
  manifest: CatalogManifest;

export interface CatalogReceiptStore {

export const KILTER_CATALOG_REQUIRED_COLUMNS = {
  climbs: ['uuid', 'layout_id', 'setter_username', 'name', 'description',
    'frames', 'frames_count', 'is_draft', 'is_listed'],
  climb_stats: ['climb_uuid', 'angle', 'display_difficulty',

  difficulty_grades: ['difficulty', 'boulder_name', 'is_listed'],

```

`CatalogInstallContext` is owned exclusively by the serialized worker; successful
activation replaces its `active` field. `active` is the queryable in-memory connection,
not the authority for which slot may be overwritten. Slot filenames and pool-directory name come
from `catalog-config.ts`, never from downloaded data. Extend the ambient VFS type only
with the verified public methods consumed here.

Algorithm:

1. Validate manifest and compressed-byte limits again at the worker boundary. Verify
   SHA-256 over compressed bytes before decompression. Read gzip incrementally with a
   hard raw-output cap, then require exact declared raw length and SQLite header,
   including rollback-journal read/write version bytes 18 and 19 both equal to 1.
2. Re-read and parse the stored receipt while holding the worker's origin lease.
   Choose the opposite of its named slot, even if that slot failed startup validation
   and the in-memory `active` connection is null. Use `a` only when the metadata key
   is absent; an unreadable or unparsable record is an error, never absence. Do not
   open for writing, truncate, or delete the stored receipt's slot. Delete/recreate
   only the chosen inactive slot through public VFS methods; no open SQLite handle
   may reference it. Import in bounded chunks, truncate to exact size, sync and close
   the raw handle. A raw or SQLite close failure, or a delete failure, poisons the
   worker: terminate it rather than reusing uncertain handle associations.
3. `inspectCatalogFile` reads the closed candidate's logical
   file via public `xOpen`/`xRead`/`xFileSize`/`xClose`: require the SQLite magic,
   rollback header bytes 18/19 equal to 1, and file size equal to `manifest.bytesRaw`.
   Then open candidate READONLY using the same registered VFS. Enable `trusted_schema=OFF`
   and `query_only=ON`, and set `temp_store=MEMORY` to keep temporary query/sort files
   out of the six-file handle pool. Read `PRAGMA page_count` and `PRAGMA page_size`
   separately and require their product to equal `manifest.bytesRaw`, with safe
   integer results. Require `PRAGMA integrity_check` to return the sole `ok` result
   and ordinary tables with every column in `KILTER_CATALOG_REQUIRED_COLUMNS`, using
   fixed-name schema introspection. Reject views or virtual tables in place of those
   tables. Require a nonempty `climbs` table whose rows all have `layout_id=8`; manifest
   board must equal `kilter-fullride-7x10`. Extra native columns/tables remain preserved.
   These exact required columns were aligned with the catalog-query implementer;
   no product, placement-role, edge, user, or unrelated source table is required by
   that consumer. The adapter binds the canonical generated definition ID/revision,
   whose native source scope is product 7/layout 8/size 17/sets 26–27, and derives
   placement/role allowlists from that definition (Fullride role IDs 42–45).
   Do not equate layout-wide climb count with 7x10-compatible climb count; the provider
   query adapter owns exact frame/placement compatibility and supported-role filtering.
4. Construct receipt; write it in one IndexedDB transaction and wait for transaction
   completion, requesting strict durability. Until that succeeds, `active` still points
   to the old queryable connection, if one exists. Set a `receiptWriteAttempted` phase
   flag before calling `write`. Before that point, candidate failure may close/delete
   it only after all its handles close successfully. Once the receipt write has been
   attempted, never delete the candidate, even if `write` rejects or times out: the
   transaction may have committed. Re-read the receipt under the same lease to
   determine the selected slot and recover the matching validated connection. If
   its commit state cannot be established, poison/terminate the worker and reopen
   through normal startup; do not return a stale `retained` receipt or attempt more work.
5. Commit point is receipt transaction completion. Immediately swap `active` to the
   already-validated candidate, then close the old connection. Failures after this point
   must never delete the committed candidate or report that the old receipt is active.
   Worker failure after commit is recovered by reopening the receipt on next startup.
   Retain the previous slot's bytes; only a later consented install reuses that slot.

On startup, open metadata only after obtaining the worker-held lease; close it on
`versionchange`. Read and validate the receipt, inspect the named slot's logical file
size and rollback header, then open it READONLY with the same three PRAGMA settings.
Validate page count times page size, required schema/identity and `quick_check` before
ready. No receipt means no active catalog, even if a staged slot exists. Unreadable/invalid receipt or active DB
means a visible recovery error, never silently choose an arbitrary file or overwrite
both slots. An explicit reinstall may proceed with a valid stored receipt even when
its database failed validation, always targeting the opposite slot. Metadata corruption
requires a separate recovery decision; this stride provides no destructive reset.

This is a staged cross-store protocol, not a claim of one OPFS+IndexedDB transaction.
For interruptions before receipt commit, old receipt and active file remain unchanged;
after commit, the fully flushed candidate is selected. Browser eviction/power-loss
guarantees still belong to platform storage; authored climbs and playlists are never
participants. Retaining the previous slot is intentional: two existing snapshots use
about 25 MB of raw catalog storage, plus metadata/pool overhead. The consumer's storage
copy must explain the two-slot allowance rather than advertise only the download size.
There is no post-commit deletion optimization. Repeating an already-active manifest
identity is a no-op only after the active catalog is validated; do not skip recovery
solely because version numbers match.

**Acceptance:** candidate I/O, decompression, validation, or receipt failures preserve
the readable active catalog; injected worker exit before/after activation selects the
correct slot on reopen; failed candidates do not consume unbounded pool capacity.

```typescript
  signal?: AbortSignal,

```

Cap manifest response at 16 KiB, compressed snapshot at 8 MiB, and raw output at
32 MiB for this slice. Require safe positive integer sizes/version, exact board and
compression, 64 lowercase hexadecimal SHA-256 characters, valid date or explicit
unknown source freshness, bounded provenance strings, and a basename matching
`kilter-7x10.v<positive integer>.db.gz`. Resolve only under same-origin `/catalog/`,
reject redirects, check HTTP success and streamed byte counts, and require exact
declared compressed size. Do not trust Content-Length as the only bound.

The current binary/digest remains unchanged; extend its manifest with a provenance
schema. `generatedOn` is the known build date, while `sourceDataThrough: null` states
the absence of a verified freshness cutoff. The build script records the input source
and generation date explicitly for future runs; it does not infer freshness from today
or run network refresh/publish in CI. Deterministic gzip metadata is appropriate when
regenerating, but do not regenerate the accepted artifact merely to alter its envelope.

The manifest shown at consent is the exact validated manifest submitted to install.
A retry must not silently acquire a different source/version. Offline ready startup
reads the receipt without fetching; network failure during an optional offer preserves
the current catalog. Abort applies to download; once activation starts, retain the
normal update-admission blocker until installation settles.

Both acquisition helpers reject with `CatalogBootstrapError` on the main thread.
Use `aborted` for signal cancellation, `network` for fetch/HTTP failures, `manifest`
for invalid JSON/schema/source/path/redirect policy, and `size` for streamed length
or declared-limit violations. Preserve known codes rather than forcing the browser
service to infer failure kind from text. The class is also the main-thread adapter's
typed rejection for worker death/timeouts; anticipated worker installation errors
remain cloneable result objects, not custom subclasses sent through Comlink.

**Acceptance:** digest, size, origin/path, gzip, malformed-manifest, network, redirect
and abort failures are explicit; source age survives offline reopen; no binary request
before consent; cached active catalog remains readable without network.

### Unit 3: Worker lifecycle and typed installation surface

**Files:** `web/src/data/catalog/bootstrap-port.ts`,
`web/src/data/sqlite/catalog.worker.ts`, `web/src/data/sqlite/catalog-db-api.ts`,
`web/src/data/sqlite/sqlite-catalog-port.ts`, `web/src/data/sqlite/catalog-db.ts`.

```typescript
export type CatalogFailureCode =
  | 'unsupported' | 'busy' | 'closed' | 'manifest' | 'network' | 'aborted'
  | 'digest' | 'size' | 'decompression' | 'schema' | 'storage';
export type CatalogStorageStatus =
  | { status: 'empty' }
  | { status: 'ready'; receipt: CatalogReceipt }
  | { status: 'unavailable'; code: CatalogFailureCode; message: string };
export type CatalogInstallResult =
  | { ok: true; receipt: CatalogReceipt; unchanged: boolean }
  | { ok: false; code: CatalogFailureCode; message: string;
      retained: CatalogReceipt | null };
export interface CatalogBootstrapPort {
  catalogStatus(): Promise<CatalogStorageStatus>;
  installCatalog(
    manifest: CatalogManifest, compressed: ArrayBuffer,
  ): Promise<CatalogInstallResult>;
}
// CatalogDbApi adds CatalogBootstrapPort to its existing query/isReady/close RPC.
// SqliteCatalogPort implements CatalogPort and CatalogBootstrapPort.
```

Use cloneable discriminated results for anticipated installation failures; do not
depend on custom Error subclasses surviving Comlink. Transfer the compressed
ArrayBuffer through Comlink so the main thread does not retain a duplicate.
Keep all database operations (`query`, status, install and close) on one worker queue;
Comlink async calls can otherwise interleave across awaits. Ready always means a
validated active connection, never merely that `open_v2` returned a handle.

Inside the dedicated worker, acquire
`navigator.locks.request('cruxcontrol-catalog-owner', {mode:'exclusive', signal}, ...)`
before pool construction or metadata open. Use an AbortController to cap queued
acquisition at 3 seconds, then report retryable `busy`; clear the timer when acquired
and hold the lock callback pending until close. This permits normal reload handoff
without immediately reporting contention. Unsupported Web Locks/OPFS returns
unsupported. Never acquire the pool lease on the main thread.

`NoModificationAllowedError` or `InvalidStateError` during pool initialization also
maps to retryable `busy`, even after the lease was acquired: worker termination does
not guarantee a fixed order between access-handle and Web Lock release. Close what
can be closed and terminate every failed initialization worker. The VFS initializes
handles with `Promise.all`; late resolutions can outlive a rejection and a best-effort
`vfs.close()`. Never retry initialization inside that worker. The main adapter retries
with a new worker. Other startup failures remain storage errors, never empty state.

Keep a main-thread dead/closed flag and track outstanding calls. Listen for Worker
`error` and `messageerror`; either rejects outstanding and future calls with
`CatalogBootstrapError('closed', ...)` and terminates the worker. Bound normal RPCs
at 60 seconds and close at 3 seconds; expiration poisons/terminates the worker and
settles pending calls rather than leaving Comlink promises unresolved. An install RPC
timeout is an unknown commit outcome: do not return an old `retained` receipt or
delete anything. The next adapter reads the durable receipt. The consumer releases
its update-admission blocker when the service operation rejects/settles or tears down.

For normal close, finish queued work, close SQLite connections, the VFS, and metadata,
then release the lease with nested `finally` cleanup. Terminate in main-thread `finally`
even when close rejects or exceeds its deadline. A raw/SQLite close or `xDelete`
failure prevents all subsequent queries/installs in that worker. Never return an
uncertain handle to the pool for reuse; no best-effort delete follows failed close.

One API/VFS instance lives for the worker lifetime, respecting the existing
`CatalogDb` once-per-API VFS registration. No new VFS of the same name is silently
substituted within one SQLite module. Startup and runtime status must distinguish
missing catalog from unsupported browser, occupied pool, and storage corruption.

**Acceptance:** a second tab cannot race import/open; closing the owner allows retry;
worker failure releases the lease; overlapping query/install/close requests finish in
order; startup storage errors are distinguishable from empty installation.

## Risks and remaining gates

- **Cross-store activation:** OPFS and IndexedDB have no shared transaction. Flush,
  validate, then commit the receipt; keep the old slot. Fault-injection acceptance is
  required before claiming interruption safety. Never overwrite the active slot.
- **Pool ownership:** AccessHandlePoolVFS does not implement SQLite locking. The
  entire pool requires application-level exclusivity, including readers. Browser
  multi-tab acceptance must verify a useful busy/retry flow rather than hang.
- **Memory/quota:** the bounded two-slot design retains up to two raw catalogs
  (about 25 MB for this snapshot), plus metadata; installation additionally needs
  compressed/decompressed buffers and SQLite memory. Report storage failure,
  preserve the active catalog, and retry; do not clear unrelated site storage.
- **Provider scope:** the historical source snapshot includes layout-wide climbs;
  it is not proof that every row fits the configured 305-placement board. The
  catalog-domain feature owns the compatibility projection consumed by browsing.
- **Native support:** this stride proves Android/desktop Chromium only. OPFS behavior
  in the iOS shell remains a separate platform acceptance question.
- **Consumer integration:** the browser feature owns community entry, consent and
  update-admission design. Its mock alignment gates that feature's UI implementation,
  not this storage feature. There is no remaining VFS-import blocker.
- **Production build:** direct-source spike success does not prove Vite bundling.
  Existing worker/WASM verification and real production browser smoke remain mandatory.
