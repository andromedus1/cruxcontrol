# Research: Cloudflare Deploy Path for CruxControl

## Context

`epic-foundation-ci-deploy` needs a concrete deploy mechanism. The foundation brief
([foundation-pwa-sqlite.md](../foundation-pwa-sqlite/parent.md) §4) recommended
"Cloudflare Pages (static, custom-header-capable)" as the host but left *how* the
deploy runs unresolved ("GitHub Actions / CF Git integration"). This brief resolves
both the **target** (which Cloudflare product) and the **mechanism** (how CI deploys),
against CruxControl's constraints: a client-only static React + Vite PWA in a monorepo
(`/web`), distributed to friends, where the project's #1 rule is "CI must be green
before ship," and where the official SQLite-Wasm build (a possible future) requires
COOP/COEP headers.

## Decision 1 — Target: Cloudflare Workers Static Assets (not Pages)

Cloudflare's official Workers Best Practices documentation now states that for new
projects you should use Workers, not Pages: "Workers Static Assets is the recommended
way to deploy static sites, single-page applications, and full-stack apps on
Cloudflare. If you are starting a new project, use Workers instead of Pages. Pages
continues to work, but new features and optimizations are focused on Workers."
`[cf-workers-best-practices]{1}`

Pages is **not** deprecated — there is no "deprecated" or "maintenance mode" language
in the Cloudflare docs for Pages, and it remains available on all plans. The honest
framing is: both work today; Workers is where new investment goes. For a greenfield
project that will live for years, choosing the vendor's forward path avoids betting on
a frozen product.

Workers Static Assets has full feature parity for everything CruxControl needs:

- **SPA serving** — `not_found_handling = "single-page-application"` returns a 200 with
  `index.html` for any non-asset request `[cf-workers-static-assets]{5}`.
- **Custom headers (COOP/COEP)** — a plain-text `_headers` file in the asset directory
  sets arbitrary response headers, documented near-verbatim to the Pages mechanism
  `[cf-workers-headers]{6}`. This preserves the foundation brief's rationale for a
  "custom-header-capable host" (keeping the official SQLite-Wasm build, which needs
  COOP `same-origin` + COEP `require-corp`, on the table). Caveat: `_headers` applies
  to static-asset responses, not to responses generated by Worker code.
- **Git builds + per-PR previews** — the native Workers Git integration auto-deploys on
  push, provides a preview URL for `wrangler versions upload` builds, and comments build
  status on PRs `[cf-workers-github-integration]{9}`.
- **GitHub Actions deploy** — "You can deploy Workers with GitHub Actions" via the
  official `cloudflare/wrangler-action@v3` `[cf-workers-github-actions]{4}`.

## Decision 2 — Mechanism: GitHub Actions + wrangler-action, deploy gated behind CI

Use `cloudflare/wrangler-action` (the deprecated `cloudflare/pages-action` README
directs all users here: it "has been deprecated… migrate to wrangler-action, which
supports Pages deployments and offers a unified tool for managing both Workers and
Pages" `[cf-pages-action-deprecated]{2}`).

The decisive factor is **CI gating**. CruxControl's #1 rule is "CI green before ship."
Cloudflare's native Git integration builds by running a single configured build command
and marks the build "failed" on any non-zero exit code and "successful" on exit 0
`[cf-pages-build-config]{10}`. The docs document no separate lint/typecheck/test stage;
success is exit-code-only. The honest framing (as with the Pages-deprecation point
above, this is an inference from what the docs do *not* provide): to gate on a real test
suite under the native integration you would have to fold the entire suite into that one
build command (e.g. `npm run lint && npm run typecheck && npm test && npm run build`), so
a failure yields a non-zero exit. With GitHub Actions, the deploy job declares
`needs: [lint, typecheck, test]`, so a red check blocks the deploy outright — the exact
coupling the project requires. GitHub Actions also keeps deploy config in git
(`wrangler.jsonc`) rather than the Cloudflare dashboard, and running build/test in
Actions avoids consuming Cloudflare's native build quota (Free plan: 500 builds/month,
1 concurrent build, 20-minute timeout `[cf-pages-build-limits]{7}`).

Tradeoff accepted: GitHub Actions requires two repo secrets and a little wiring for
preview deploys (vs. the native integration's free, automatic previews). If preview
wiring proves not worth maintaining, the native Workers Git integration can be layered
on later for previews while Actions remains the gated production path
`[cf-workers-github-integration]{9}`.

## Implementation Notes

- **Secrets** (you provide before the deploy step can run):
  - `CLOUDFLARE_API_TOKEN` — for the recommended Workers deploy, create the token from
    the **`Edit Cloudflare Workers`** API token template (Account API tokens → Create
    Token → Custom → "Edit Cloudflare Workers"); the Static Assets docs state no
    additional permission `[cf-workers-github-actions]{4}`. (For reference, the rejected
    Pages path uses the Account → Cloudflare Pages → Edit scope `[cf-ci-direct-upload]{3}`.)
  - `CLOUDFLARE_ACCOUNT_ID` — the account to deploy to `[cf-workers-github-actions]{4}`.
- **Monorepo `/web`** — either set the action's `workingDirectory: "web"` and deploy the
  built `dist`, or run from repo root and deploy `web/dist`; both are documented
  primitives `[cf-wrangler-action]{8}`.
- **Workflow shape** — jobs `lint` / `typecheck` / `test` (run on PR and push to main),
  plus a `deploy` job `needs: [lint, typecheck, test]` that runs only on push to main
  and uses `cloudflare/wrangler-action@v3` `[cf-workers-github-actions]{4}`. The
  canonical Pages-deploy workflow YAML (adapt the `command:` for Workers) is in the
  Cloudflare CI guide `[cf-ci-direct-upload]{3}`.
- **Previews** — produce a preview deploy for non-production branches/PRs via wrangler's
  branch/version flags; the action triggers on the current branch unless a branch option
  is set `[cf-ci-direct-upload]{3}` `[cf-wrangler-action]{8}`.
- **wrangler config in git** — `wrangler.jsonc` carries `name`, `compatibility_date`,
  and `assets` (directory + `not_found_handling: single-page-application`)
  `[cf-workers-static-assets]{5}`.
- **Catalog snapshot hosting** — `epic-foundation-catalog-bootstrap` decided to host the
  pruned `kilter.db` as a same-origin static asset; on Workers Static Assets this is just
  another file in the asset directory. Re-confirm the per-file size limit on Workers
  Static Assets during that feature's design (Pages' limit is ~25 MiB/file; verify the
  Workers figure).
